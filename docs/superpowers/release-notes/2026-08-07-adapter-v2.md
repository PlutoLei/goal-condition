# goal-condition adapter v2 —— 发布说明

发布日期：2026-08-07
release commit：见 `~/.claude/goal-condition-trust.md` 的最新一行（manifestDigest 同表）

本版把两个 runtime 的启动适配层从「文档描述」变成「可执行代码」：新增 `scripts/launch.mjs` 与
`scripts/lib/adapters/{claude,codex}.mjs`，公开闭包 `REQUIRED_CORE_FILES` 由 12 项增至 15 项。
协议核心（contract 格式、canonical hash、snapshot、controller-owned 证据通道、独立 postflight）不变。

## 破坏性行为变更

升级前请逐条对照，已有 contract 与编排脚本可能需要改动。

1. **finalize 通道名改绑**：`finalizationReceipt.operation` 由 `update_goal` 改为 `thread/goal/set`，
   `runtimeReadback.source` 由 `get_goal` 改为 `thread/goal/get`。**旧通道名的 receipt/readback 一律被拒。**
   根因：`update_goal`/`get_goal` 是线程内模型侧 tool，外部编排器没有调用通道，旧指令按字面无法执行；
   app-server JSON-RPC 才是真实表面。

2. **claude runtime 不再支持 `enforcement:"physical"`**：任何 physical 约束在 launch 前置闸一律红，
   必须改写为 `audit_only`。原因是 claude adapter 生成的 deny 规则只保护控制器自己的机件
   （hook 脚本与 state 目录），不存在面向用户约束的物理拦截面。此前有一种形态（mechanism 逐字照抄
   一条 deny 规则）能通过，现已一并收紧——那本来也是不动点陷阱（deny 路径含 contract 自身的 hash）。
   codex runtime 的 physical 约束仍受支持，但只认 `--sandbox` 这一个物理面：mechanism 不指向 sandbox
   的（proxy、只读凭证等）同样红。

3. **`budget.max_turns` 必须是整数**：含小数 `max_turns` 的既有 contract 会失去 launch 资格，
   需重编译、重 preview、重确认。原因是该值在两处被 floor（CLI 的 `--max-turns` 与 hook 的
   `maxBlocks`），小数会让两处一起塌成 0，即「什么都不做」而非 fail-closed。
   `max_minutes`/`max_cost_usd` 的小数有真实语义、`max_tokens` 原样透传不经我方取整，故均不受此限。

4. **launch/resume 的退出码**：终局报告（`outcome=terminal_report`）现在 exit 3，不再是 exit 0。
   退出码语义：`0` 产出了候选（**仅表示 envelope 形状合法，不代表 run 成功**——`is_error:true` 的
   结果同样是候选、同样 exit 0，成败由状态机判）/ `1` 进程级失败 / `2` usage 或参数错误 /
   `3` 终局报告：被前置闸挡下没起飞，**或起飞后判定终局**。
   ⚠️ **exit 3 不等于「什么都没跑」**。判别式是返回体的 `attemptNumber`：为 `null` 才是从未起飞；
   非 null 表示执行器已 spawn，**必须按可能已改仓处理**，照常跑 snapshot verify。
   仅按退出码判成败的编排器需要跟改。（权威判据始终是 stdout 报告体的 `outcome`/`reasons`，
   协议本来就要求把 `runtimeResult` 喂给 `nextAction`。）

6. **launch/resume 返回体的 `attemptNumber` 可能为 `null`**：此前它恒为正整数；现在被前置闸拒绝时
   为 `null`（那种情形连 `attempts/` 目录都不会建）。对该字段做类型校验、闭世界形状校验或直接
   算术的消费方需要跟改。配套的口径变更：**被前置闸拒绝的调用不再消耗 attempt 配额**——改正
   binding 笔误、版本、hook 模式等 contract 之外的原因后，配额仍是满的。
   （codex 侧有一处例外:过了前置闸但在 auth-copy/daemon 连接阶段失败的,仍会占号,见 `codex.md`。）

5. **git preflight 谓词只在 capture 阶段判定**：`require_clean`/`require_branch`/`require_upstream`
   在 postflight 的 `snapshot verify` 阶段不再重跑，git 边界完全交给 baseline compare。
   这修复了「`require_clean: true` 与同仓内任何文件变更互斥」的结构性缺陷——旧版下，run 只要产生
   一个 `allowed_mutations.files` 明确允许的文件，verify 就必红，且诊断 `next` 会指引操作员删掉
   刚产出的成果物。**方向是放宽 verify、不放宽边界**：未声明的变更仍被 compare 以更精确的诊断拦下。

7. **codex 侧 attempt 配额口径与 claude 侧对齐（后续加固轮）**：占号从「函数入口」挪到
   「`start`/`initialize` 成功之后」。此前三种「什么都没发生」的失败——`auth.json` 缺失（没登录）、
   codex 二进制缺失、daemon 起不来——照样烧配额，连撞三次即把这份 contract 在该 state 目录上永久
   锁死；且它们的 reason 谎称「执行器可能已改仓」，会把操作员推去做无谓的 snapshot verify。
   现在这三类一格不占、reason 如实说明「工作目录未被触碰」，并且会把本次 `mkdtemp` 出来、从未连上
   过的 codexHome 删掉、**不写** `codex-home.path`（保证指针与 `thread.json` 始终自洽）。
   反向不变：一旦连上 daemon，之后的任何失败仍照常占号、仍保留「可能已改仓」的警告。

8. **`finalize` 归因不成立时 exit 3**（此前 exit 0），与 `launch`/`resume` 的终局报告同一格。
   两份证据文件仍写 `ok:false`——权威判据始终是它们的 `ok`，退出码只是对齐后的粗信号。

9. **codex 版本闸收紧**：此前只校验 `codexVersionRaw` 非空字符串，而 `prepare` 探测失败时写的是
   `"probe failed: …"`（非空），于是「codex 根本没装」也能过前置闸。现在必须解析得出版本号形态。

⚠️ **两个 runtime 的返回体仍不对称**：claude 侧用 `attemptNumber`（`null` = 从未起飞）作判别式，
codex 侧的返回体**没有**这个字段，调用方无法据此判断「这一轮到底占没占号」。对齐属返回体形态变更，
留作后续。

## 已知限制

以下均已在代码或 spec 中如实记录，此处汇总。都是 fail-closed 方向，不构成安全缺口。

- **孤儿 daemon**：controller 被 SIGKILL 后，app-server 依赖 stdio EOF 自退——**本轮未实测，代码不依赖
  这一点**。「不会出现两个并发执行器」的保证来自 launch 前置闸拦住 stale 租约，出口是先跑 `close`。
  （spec 早期版本曾写「租约 TTL 到期 → daemon 侧自动 clear goal」，该机制并不存在，文档已更正。）
- **TOCTOU 窗口**：settings 覆写与 `execFile` 之间仍有窗口，同 uid 进程可在窗内改写。真正关闭需要把
  内容直接喂给子进程或用 fd 传递，受 `claude -p` 的 CLI 表面限制，本轮不做。
- **信号竞态（已修一半）**：`withCodexClient` 的 cleanup-then-continue 窗口，信号在 client 构造
  **之前**到达那一半已修（中止标志置位后不再启动）；**中止之后仍会起 turn** 那一半原样存在。
- **`REQUIRED_CORE_FILES` 的守护现在是单点**：闭包完整性由 `static.test.mjs` 的磁盘对账测试独扛
  （真相源是 `readdirSync` 的真实文件树，与常量无关，删/加任一项都能抓）。此前分散在
  `install.test.mjs` fixture 上的偶然覆盖已随 fixture 改为常量派生而消失——这是有意的架构收敛，
  但那条测试**不可当作冗余删除**，删掉即恢复「删 12/15 项零反应」的盲区。
- **`claudeVersion` 是 `probes.json` 里唯一仍被读的判定输入**：篡改它只能放松版本闸，不影响
  hook 完整性与 settings 两道；其余判定输入均在每次 attempt 现场重算。
- **`REQUIRED_CORE_FILES` 自引用**：15 项里删掉 12 项，测试仍全绿（真正的守护在 `install.test` 的
  fixture 而非常量本身）。保护是单向的：常量多一项会被抓，少一项基本不会。
- **`finalize` 的退出码未跟随第 4 条**：归因失败时写 `ok:false` 但仍 exit 0。其证据文件有明确消费
  路径（喂 `nextAction` 会被拒），故留作挂账。
- **`pressure-evidence.json` 的协议漂移**：该 fixture 记录的是 2026-08-05 版指令文本，其中仍含
  `update_goal`/`get_goal` 字样，与本版通道名不一致。**它是历史模型采样证据、带自校验 hash，本轮
  刻意未重跑**（重跑 5 场景 ×2 变体的成本未被授权）。读它时请按旧协议文本理解。
- **Launch 层信任 Validate 已执行**：字段级政策（如 `max_turns` 整数）只有 validator 一个执行点，
  launch 层不复查。这与本仓多处不变量同形（target_roots 唯一性、argv 非空亦然），是设计而非疏漏；
  兜底来自 `nextAction` 仅在 `validation` 为空数组时才返回 `launch`。

## 验证与实测基础

- 单元测试 237 项全绿（基线 119 → 237）。
- 两次真实端到端冒烟（claude runtime，走已安装 release 的 symlink 路径）：第二次一次走通、
  未改 contract，`nextAction` 返回 `complete`。
- 三轮全分支对抗式终审 + 两轮冒烟共发现 20 条问题（Critical 0 / Important 7 / Minor 13），全部已修。
  其中 4 条只有真实运行才暴露得出来——包括「经 symlink 调 launcher 会静默 exit 0」这一条，
  而已安装 skill 的路径恰恰就是 symlink。
