# 原生 goal 的共享语义

本文件是 Claude Code 与 Codex 两个 goal-condition skill 共用的唯一语义源。仓库根目录 `shared/goal-semantics.md` 是正本，两个 skill 的 `references/goal-semantics.md` 是逐字节副本，由测试守住一致。启动方式、长度上限、预算接口、状态与停止行为属于各 runtime 的 SKILL，不写在这里。

## 目标

- 一个 goal 只承载一个一致的、可观测的结果。这个结果可以由几项必要验收共同构成；互相独立、可以分开完成的几件事不是一个 goal。
- 输入含多个独立目标时，让用户选一个。不得静默合并，也不得为拆分而自行启动子 goal。
- 写终态、验收项及其检查方式、要紧的约束、非目标、停止条件。检查方式可以包含验证命令、前置条件、必要依赖与恢复条件。
- 不写实现配方。怎么做属于执行模型在授权范围内的判断。
- 缺失信息只在会导致两个实质不同、且无法采用保守默认的结果时才问一个问题。

## 授权

- 研究、规划、改写 skill 都不等于启动 goal。普通的任务授权也不等于 goal 授权。
- 只有用户明确要求以 goal 方式执行（或批准了 goal 提议）时才启动原生 goal。已经批准的设计再被要求执行时，不再重复确认同一件事。
- 本 skill 不授予任何额外权限。宿主沙箱、审批模式与项目规则照常生效；付费运行、发布、部署、凭据访问等外部效果需要与该动作相称的授权。
- 已有未完成的 goal 时继续它，不另起重复的 goal、调度器或子进程来维持执行。

## 预算

- 只记录用户明确给出的资源上限，并带上单位。用户没给就省略，不编造默认值，也不把"没说"当成可以花费的许可。
- 目标达成与预算耗尽分开报告。预算将尽不是标记完成的理由。

## 证据标准

两个 runtime 的完成判定者不同，但证据标准相同：

- 每一项要紧的完成主张，都绑定到本次运行中、最后一次相关改动之后的新鲜观察。
- 证据写明它验证的对象：路径、commit、产物哈希、run ID 或服务端标识，不写"测试通过了"这类无主语的结论。
- 缺失、过期、间接、只是"与完成相符"的证据都按未通过处理。计划中的测试不是通过的测试。
- mock 证据只证明 mock 的契约。工程检查、真实服务或算力结果、科学验收是三个不同的层级，低层级的绿不能推出高层级。
- 失败时在范围内诊断、修复并重跑受影响的检查。没有新证据的重复尝试要换诊断，不能放宽判据、删掉必需交付物，或把没跑的检查改标成不适用。

判定者差异要如实对待：Claude 的独立评估器只读对话记录，不能核实文件；Codex 由执行模型自审。两者都不是对产物的独立验证。高风险任务需要执行体之外的独立核验，由项目规则或受控通道提供。

## 完成的命名

原生 goal 的完成只叫"完成"，不叫 `Certified Complete`，也不能由此推出任何控制器认证。项目若仍要求旧认证，先迁移该项目的门槛，再把受治理的工作交给原生 goal。
